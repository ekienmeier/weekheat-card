## Verdict

The design is good: the decisions are sound, written down, and kept to. Writing only when the
scheduled temperature changes, keeping all configuration in Home Assistant, using one day script for
both the card and the automations, and the room directory for non-admin users are all good choices.
Hardware quirks are handled with care and with evidence. The exported logic at the top of the card is
pure and well tested.

The implementation has not kept up with the design. The card is one class of 1,232 lines of code that
does everything: loading, publishing, computing a room's status, writing to Home Assistant, handling
events, holding the UI state and rendering. The code is squeezed into very long lines, so it looks
about half its real size. The logic that decides what a room is doing (manual, window open, valve
closed, heating) sits in methods that read `this._hass` and has no tests. The room blueprint is a state
machine of about 420 lines of Jinja, tested only by hand on a live system. Several rules exist twice
(card and blueprint) with nothing to check that they agree.

The review found four defects that cause wrong heating or lost data (H1–H4). They should be fixed,
with regression tests, before any refactoring.

## What is good and should stay

- **The pure-logic part** of the card (lines 1–429): exported, free of the DOM, tested. The refactoring

- **The design document**: the decisions, their reasons and the live tests, with dates. Rare and valuable.

  and the card stores nothing of its own.
- **Workarounds with evidence**: HomeKit ignoring `hvac_mode` (yaml:622), `hvac_action` always

## Findings

Severity: **High**: wrong heating, lost data or a security hole now. **Medium**: a likely defect, a
risk, or a large cost to every future change. **Low**: worth fixing when the code is touched.

### High

#### H1. The state helper overflows with four thermostats; the room then stops working properly

*Where:* weekheat_room.yaml:387 (`stamp`), written at :435, :456, :503, :591 and :655; created with
`max: 255` at card:815. The card lets a room have any number of thermostats.

Each thermostat's entry is `"<entity id>":[21.5,"2026-11-13T06:00"]`: about 29 characters plus the
entity id. 20 of them are the timestamp, and **nothing reads it**: the blueprint reads only `[0]`
(:453, :499, :560, :617), and the card never reads it. With entity ids of about 35 characters
(`climate.wohnzimmer_thermostat_couch`):

| Thermostats | Normal | While the room sensor holds the valves | Same, without the timestamp |
|---|---|---|---|
| 2 | 129 | 172 | 134 |
| 3 | 195 | 243 | 186 |
| 4 | **258** | **311** | 235 |

Home Assistant does not store a value longer than the helper's maximum, so the room's state stops
being saved. Two consequences:

- The next run (at most 15 minutes later) still sees the old "last applied" value and writes the plan
  again. A change made by hand no longer holds until the next period, which is the core promise.
- When a window opens, the setpoints from before are not saved. When it closes, the run sees nothing
  to restore and nothing new to write, so **the room stays at 5 °C** until the next period with a
  different temperature.

Nothing tells the user; only a warning in the log shows it (`input_text` drops a value over its
maximum and returns, so the run itself does not fail).

*Fix:* remove the timestamp (unless it is wanted for diagnostics; it is documented in design.md but
used nowhere). Add a pure function for the worst-case state size, and have the card refuse or warn
when a room would exceed 255. Have the blueprint check the length before `input_text.set_value` and
raise a persistent notification rather than fail silently. Changing the stored format needs a
migration note in the release.

#### H2. A plan name can select the wrong plan, in the card and in the automation

*Where:* `matchPlan`, card:217–225; `named_plan`, weekheat_room.yaml:367–376 (the same rule).

A plan matches a name when its entity id ends with `_<slug>` or its friendly name ends with
` <name>`, and the first plan in the list wins. Run against the current code:

```
matchPlan('Werktag',    [..._kurzer_werktag, ..._werktag])     → schedule.weekheat_bad_kurzer_werktag
matchPlan('Homeoffice', [..._kein_homeoffice, ..._homeoffice]) → schedule.weekheat_bad_kein_homeoffice
```

So an exception "Plan: Werktag" or a keyword rule naming "Homeoffice" can heat by another plan whose
name ends the same way. Because the card uses the same rule, the day list shows the same wrong plan,
and nothing looks wrong. (New plans are added at the end of the list, which hides this until a plan
is deleted and made again, or the list is reordered in HA's editor.)

*Fix:* match exactly first: the plan part of the friendly name (`planLabel`) equals the name, ignoring
case, or the entity id equals `schedule.weekheat_<room>_<slug>`. Fall back to the suffix match only
when exactly one plan matches. Make the same change in both places, with a unit test and a consistency
test.

#### H3. *Add room* can overwrite a room that the card does not show

*Where:* `_addRoom`, card:806–836.

The check for an existing room uses `this._rooms` (:811), which holds only the rooms the `rooms:`
option shows, not `this._allRooms`. The automation id is `weekheat_<slug>`, so "Bad" and "Bad!" give the
same id, and a name without letters or digits gives `weekheat_`. In these cases
`POST config/automation/config/<id>` replaces the hidden room's automation: its thermostats, plans and
week are gone, and its plans and state helper are left behind. There is also no clean-up when a later
step fails: the plans, state helper and switch made so far stay.

*Fix:* check against `_allRooms` and against every automation id in HA's states. Refuse an empty slug.
On failure, delete what was made.

#### H4. One failed read removes rooms for every non-admin user

*Where:* `_load`, card:484–502.

Each automation's configuration is read with `.catch(() => null)` (:487), the day script's with
`.catch(() => null)` (:491), the blueprint lists with `.catch(() => ({}))` (:492–493). The result is
then published as the room directory (:502), which every non-admin card uses. A single failed read
(HA busy after a restart, a flaky phone connection, a timeout) removes that room from all other users'
cards until an admin's card loads again. A failed script read publishes `script: false`, and their
cards then say the day script is missing.

*Fix:* treat "this automation is not a Weekheat room" (no `use_blueprint`, or 404 for automations not
made in the UI) differently from "the read failed". On a failed read, stop the load, show the error and
publish nothing.

### Medium: correctness and robustness

#### M1. Unsaved edits are thrown away without warning

*Where:* `_draftFor`, card:1020–1030, and the actions that reset it: :1143, :1146, :1149, :1155, :1161,
:1170. One draft holds a room's plans, week and setup together, and every save or cancel resets all of
it. Saving plan A drops unsaved edits of plan B. *Cancel* in the Week tab (it uses `reset-plan`,
:1611) drops plan edits. Saving the room's setup drops both. Because the new draft is built from the
saved state, the "not saved" marker disappears too.

*Fix:* one draft per editor (each plan, the week, the setup), saved and reset on its own. Ask before
throwing away a dirty draft.

#### M2. Text being typed is lost on a forced re-render

*Where:* `_render(true)` from `_load` (every 10 minutes, :536), `_flash` (:713 and :715) and the
notification subscription (:581). Inputs commit their value on `change`, which fires only when the field
loses focus. A forced render replaces the whole card while a field has focus, so what was typed since
is lost, and so is the focus.

*Fix:* keep input values in state on `input`, or (better) update the DOM in place so that a focused
field is never replaced (Lit does this).

#### M3. Notification banners stop working after the card is detached once

*Where:* `set hass`, card:453–460; `disconnectedCallback`, :467–472.

`_subscribe()` runs only when the card receives `hass` for the first time; `disconnectedCallback`
ends the subscription. Home Assistant detaches cards and attaches them again (switching dashboard
views, editing the dashboard), and from then on the "applied late" banners neither appear nor go
away. For non-admins, the directory watch also stops until the next 10-minute reload.

*Fix:* subscribe in `connectedCallback` once `hass` is there, unsubscribe in `disconnectedCallback`,
as Home Assistant's card documentation asks.

#### M4. A failing day script stops all of a room's handling

*Where:* weekheat_room.yaml:362. Every run calls the day script first, without `continue_on_error`.
If it fails (for example, the Workday sensor is unavailable, so `workday.check_date` has no target;
or every calendar is unavailable, so `calendar.get_events` has none), the run stops before open
windows, the heating switch and the room sensor are handled, although none of these need the day
decision. Calendars that are unavailable are skipped with a warning as long as at least one remains,
so the common case already works.

*Fix:* `continue_on_error: true` on the call, and a fallback day from the Workday sensor's `workdays`
(or Monday to Friday) when there is no response. In the day script, drop calendars that have no state
before calling `calendar.get_events`. Check on a test instance which failures `continue_on_error`
covers (Home Assistant's docs: not configuration errors).

#### M5. Fixed waits are used to synchronise with Home Assistant

*Where:* card:734 (1,500 ms, "the automation reloads"), :862 (500 ms), and three copies of a 20 × 250 ms
polling loop (:745, :773–777, :827–830). On a busy Raspberry Pi the wait can be too short; on a fast
system it is wasted time.

*Fix:* one `waitFor(condition, timeoutMs)` in `ha/` that waits for the actual event (the entity
appears, the automation has reloaded).

#### M6. Errors are swallowed, and the ones shown are English only

*Where:* 14 places (card:442, 470, 471, 487, 491, 492, 493, 505, 551, 563, 564, 583, 626, 1118). Some are
right (no `localStorage`, the state helper not being JSON), but several hide real failures (H4) or assume
"older Home Assistant" without checking. `dismiss` (:1212) calls a service with no error handling at
all. The errors that are thrown are English-only text (:731, :778, :808, :811, :841).

*Fix:* follow 2.3 of the guidelines: catch only what can be handled, with a comment; texts for errors
in `i18n/`.

#### M7. An admin's card reads every automation's configuration every 10 minutes

*Where:* card:485–487. In a home with 300 automations, that is 300 REST calls per open admin card per
10 minutes, and again after every *Add room* and blueprint update.

*Fix:* the WebSocket command `search/related` with `item_type: 'automation_blueprint'` and the room
blueprint's path lists exactly the automations made from it (Home Assistant's search integration
supports this item type); then read only those.

### Medium: security and accessibility

#### M8. HTML is built by hand, and some values are not escaped

All markup is built as strings and assigned to `innerHTML`, with `esc()` called by hand for each of
about 200 values. Eight are already not escaped: `data-room="${room.id}"` (:1399, :1409),
`data-v="${r.id}"` (:1624), `data-v="${s.entity_id}"` (:1633), `data-v="${d.date}"` (:1754),
`value="${x.entity_id}"` (:1781), `data-v="${c.entity_id}"` (:1790), and a CSS selector built from
`room.id` without `CSS.escape` (:929). Today this is hard to exploit: entity ids are slugs, and
automation ids are set by admins. But room ids reach non-admin users' browsers through the directory,
and in an admin's browser the card holds a token that can change anything. The safety of the card
depends on nobody ever forgetting one of the 194 `esc()` calls.

*Fix:* build markup with a tagged template that escapes by default (about 30 lines, no dependency) or
with Lit. Add `eslint-plugin-no-unsanitized`.

#### M9. Much of the card cannot be used with a keyboard or a screen reader

- Room rows (:1393), day rows (:1754), period rows (:1571), chart segments (:1357) and two settings
  headers (:1638, :1642) are `div`s with click handlers: no focus, no role, no keys. **A room cannot be
  opened with the keyboard.**
- Every click re-renders the whole card, so focus is lost after each button press (the dial and the
  slider restore it; nothing else does).
- `↑` and `✕` in the keyword rules (:1787–1788) have no `aria-label`.
- The dial says `aria-valuemin="5"`/`aria-valuemax="30"` (:1432) whatever `dial_min` and `dial_max`
  are; the slider uses the right values. Neither has `aria-valuetext` ("Off", "21 °C") or supports
  Home, End, Page Up and Page Down.

*Fix:* buttons for everything clickable; a render that keeps focus (M2); the slider pattern of the
guidelines (2.6).

### Medium: design and maintainability

#### M10. One class does everything

`WeekheatCard` (card:438–1800) does eight jobs: the Home Assistant element, loading data, publishing
the directory, computing a room's status, writing to Home Assistant, handling pointer, keyboard and
click events, holding the UI state, and rendering every view. `_act` (:1032–1216) is a `switch` over 45
action names that mixes UI state, validation, writes to HA and `confirm()` dialogs; `_change`
(:1218–1255) has 22 more. 22 functions are over 15 lines (40 once formatted). See the plan below.

#### M11. Squeezed code hides its size

412 lines are over 100 characters, 132 over 140, the longest 391. Lines hold several statements
(:591 has seven, also :1143, :1155, :1169). Ternaries are nested up to eight levels deep (:1506,
:1508). This makes diffs and reviews hard, and it makes the line limits meaningless unless the code is
formatted first: formatted, the file is 3,185 lines.

#### M12. Short names hide meaning

`h`, `n`, `nn`, `st`, `sa`, `sw`, `so`, `d`, `dp`, `ap`, `ed`, `fr`, `L`, `t`. `n`, a room's status, is
used in about 40 places; `t` (the texts) in a heating app reads as a temperature. The CSS has `prow2`
next to an unused `prow`. Action names such as `p-step`, `ar-th`, `s-hol` and `x-day` have to be looked up.

#### M13. Comments and types are missing where they matter most

49 of 108 functions have no comment, among them all the large ones (`_act`, `_load`, `_bind`, `_change`,
`_render`, `_renderControl`, `_renderPlan`, `_addRoom`). The class has no comment. There are no JSDoc
types. The shapes passed between parts of the card are described nowhere in the code: a room, a
room's status (`n`, 18 fields), a period, a day, the UI state (`_ui`, 17 fields, 7 of them missing
from its initial value at :444), a draft.

#### M14. The status rules are coded twice, and the two disagree

The order paused → valve exercise → heating off → window open → valve closed → manual → heating →
scheduled is coded in `_status` (:1365–1378) and again in `_ctlStatus` (:1504–1510), with different
colours: a room whose valves are closed by the room sensor is green in the list but grey or orange on
the dial. `manual` and `heating` are each computed twice, in `_roomNow` and `_thNow`, with the same
tolerances.

*Fix:* one pure `roomMode(status)` that returns the mode, and one table from mode to icon, colour and text.

#### M15. Rendering changes state

`_picker` sets `ui.pick` while rendering (:1721). The views create drafts as they render
(`_draftFor` at :1545, :1603, :1657). `_render` restores focus through a `pickFocus` field. So what
happens depends on what was rendered and in which order.

#### M16. Rules that exist in the card and in a blueprint are not checked against each other

- Exception titles: card:237–238 and weekheat_day.yaml:148–150.
- Plan-name matching: card:217 and weekheat_room.yaml:367 (and see H2).
- Tolerances and limits: 0.25 °C "same setpoint" (card:638–639, yaml:350, :527, :645), 0.05 °C "same
  wanted value" (card:48, :697, yaml:455, :502, :561), 5.05 °C "above off" (yaml:262, :440, :537, :596),
  10 °C "set by hand" (yaml:504), 0.2 °C "heating" (card:649, :664).
- Input ranges: margin 0.1–3 (card:1085, :1168; yaml:143–144), window delay 0–900, exercise wait 10–600.

Only the blueprint version is checked by a test today. *Fix:* named constants on both sides and
consistency tests that read the YAML.

#### M17. The room blueprint is a large implicit state machine

One run of about 420 lines handles six modes (off, open, hold, restore, rc, plan) plus *close*, with the
transitions spread over seven `if` blocks. The inputs are normalised again and again (`[x] if x is
string else x | list` five times; the valve exercise does it once more because it runs before `th_list`
is defined); "available" is checked six times; "remove `_open` and `_rc`" is written three times. It
departs from the HA YAML style guide in a few places (inline mappings at :53–59, `to: ~` at :250).
Its templates are short (the longest has 12 lines), which is good. The day script's `out` template
has 54 lines (weekheat_day.yaml:126–180) and must be split (each rule as its own variable).

*Fix:* normalised inputs and named constants in the top-level `variables:`; one comment per step;
the mode table in design.md updated to include `rc` and `close`.

### Medium: tests and tooling

#### M18. The most important logic has no tests

The 17 tests cover the pure helpers well. Not covered: a room's status (`_roomNow`, `_thNow`: manual
detection, the order of states, the HomeKit heating heuristic), `esc` (the only XSS guard), the texts
(both languages have the same keys today, but nothing checks it), any DOM behaviour, and any blueprint
logic (six modes, the room sensor's hold time, the valve exercise). The blueprints were tested live, as
design.md records, but those tests cannot be repeated.

*Fix:* move the status logic into pure functions and test it. For the blueprints, set up tests
against a real Home Assistant core (`pytest-homeassistant-custom-component`), starting with the cases
listed under *Testing* in design.md.

#### M19. No formatter, linter, type check or CI

The tests run only when someone runs them. Nothing checks formatting, the size rules, JSDoc, types,
the YAML or the HACS requirements. *Fix:* section 3 of the guidelines.

## Refactoring plan

Each step leaves the tests green and can be released on its own. Steps 1 and 7 change the blueprints;
their releases say so (the card's update banner then offers the new blueprints).

1. **Fix H1–H4** with regression tests: a patch release.
2. **Tooling**: Prettier, ESLint with the guideline rules, `tsc --checkJs`, yamllint, CI. Existing code
   gets warnings, new modules errors. Format the card once, in a commit of its own.
3. **Domain**: move the remaining logic out of the class into pure, tested modules: room status and
   mode (M14, M18), formatting (L5), limits and constants shared with the blueprints (M16), state size (H1).
4. **ha/**: all calls to Home Assistant, `waitFor` (M5), the error policy (H4, M6), `search/related` (M7).
5. **State**: a store with typed UI state and one draft per editor (M1, M13, M15); actions grouped by
   feature in place of `_act` and `_change`.
6. **UI**: views per feature from small render functions, an escaping `html` tag or Lit (M8), focus
   kept across renders (M2, M9), buttons and ARIA (M9); texts and styles in their own modules (L2, L3, L6).
7. **Blueprints**: normalised inputs and constants at the top, the day script split, fail-soft (M4),
   the state size guard (H1), the mode table (M17); tests against a Home Assistant core (M18).

## Decisions needed before the refactoring

1. **Bundling.** (a) Bundle the modules with esbuild into the one `weekheat-card.js`, as installed
   today (recommended: nothing changes for users; one development dependency; the release builds the
   file). (b) Serve the modules as they are from `dist/`, without a build. HACS downloads every `.js`
   file there, but only the main file gets HACS's cache-busting tag, so after an update a browser may
   mix new and cached old modules unless every import carries the version.
2. **Rendering.** (a) Lit: escapes by default and updates the DOM in place, which fixes M2, M8 and most
   of M9 at once (about 5 KB compressed, so it needs the bundler). (b) Keep `innerHTML` with an own
   escaping `html` tag: no dependency, but every render still replaces the card, so focus and typing
   need workarounds.
3. **Blueprints and the size rules.** The guidelines assume: 15 lines per template and step, one file
   per blueprint (1.3). The alternative is to move the valve exercise into a blueprint of its own, which
   makes the room blueprint smaller but gives users a third blueprint to install.
